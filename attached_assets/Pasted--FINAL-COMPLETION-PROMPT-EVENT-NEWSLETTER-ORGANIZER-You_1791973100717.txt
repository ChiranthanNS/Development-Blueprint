## 2. The product: a simple event categorization and newsletter organizer

The application should do one job exceptionally well:

**Upload → Automatically categorize → Manually correct → Preview → Download → Start another project.**

Remove or simplify confusing sections, unnecessary configuration panels, redundant buttons, and features unrelated to this workflow.

The website must be clean, modern, responsive, intuitive, and suitable for real users.

## 3. Step 1 — Upload a file

The first screen should present one obvious upload area.

Allow users to upload supported files such as:

- DOCX containing event details, including tables.
- PDF containing event information.
- Images where supported by the current application.

Support drag-and-drop upload as well as a normal file picker.

Show the selected filename, file type, size, upload/processing progress, and clear errors when a file cannot be processed.

Validate file types and sensible size limits. Do not pretend a file was successfully processed if extraction failed.

Provide one clear primary action: **Analyse and Organize**.

Do not ask the user to configure numerous options before the analysis begins.

## 4. Step 2 — Extract and categorize events automatically

Extract the event information from the uploaded file as accurately as possible.

Preserve relevant information such as:

- Event name
- Event date or month
- Event description
- Event type
- Associated event images
- Other useful information actually present in the source

For DOCX files containing tables, correctly read the table rows and associate each event with its own data and images. Avoid mixing details between neighbouring events.

For PDFs, extract text accurately and use existing OCR support for scanned pages where possible.

Automatically categorize events based on their content. Use a sensible set of categories, such as:

- Workshops and Training
- Seminars, Talks and Guest Lectures
- Technical Competitions and Hackathons
- Non-Technical Events
- Outreach and Community Activities
- Department Activities
- Student Achievements
- Faculty Achievements
- Placements and Career Success
- Other / Needs Review

These are suggested default categories, not a reason to force every event into an unsuitable category. Reuse any relevant category structure already established by the project.

Do not silently discard events, descriptions, dates, or images.

Avoid duplicate events where possible. When classification is uncertain, mark an event **Needs Review** instead of pretending the classification is certain.

Show the number of events extracted and make missing information or extraction problems visible.

The user's job should be to verify the result, not manually classify every event from scratch.

## 5. Step 3 — Category review with drag-and-drop

This is a core feature and must be implemented properly.

Create a visual category workspace inspired by the usability of iLovePDF's editing experience. Do not copy its branding or build a complete PDF editor.

Show the detected categories as clear columns, panels, or grouped sections.

Each event should appear as a compact, readable card showing its title, date when available, a short description, and a thumbnail when an image exists.

The user must be able to:

- Drag an event card from one category and drop it into another.
- Move an event back to its original category.
- Change an event's category using an accessible alternative to dragging, such as a dropdown.
- Edit an event's title, date, description, and category.
- Inspect its associated images.
- Remove an event if the user explicitly chooses to do so.
- See the number of events in each category.
- Identify events that still need review.

When an event is moved, its category must update immediately and consistently throughout the application.

Drag-and-drop must work on desktop and remain usable on mobile, where touch interactions may be difficult. Provide keyboard-accessible alternatives where practical.

Do not lose the event's data or image when moving it between categories.

Use a proper drag-and-drop library already installed in the project if possible. Add a new dependency only when justified.

The user must be able to finish reviewing the categories without navigating through unrelated dashboards, reports, or settings.

Provide a clear **Continue to Preview** action.

## 6. Step 4 — Generate and preview the final draft

Generate a real document preview from the reviewed events.

The preview must reflect the actual output, not just a list of event titles.

Organize events by the categories selected by the user. Each category should have a clear heading, and each event should have a clean layout with its title, relevant date, description, and associated images where available.

Use a professional newsletter-style visual design with:

- Consistent typography
- Proper spacing and margins
- Clear category headings
- Readable paragraphs
- Sensible image sizing and alignment
- Consistent page numbering where appropriate
- No overlapping or clipped content
- No unexpectedly blank pages
- No orphaned headings where reasonably avoidable

Use the reference newsletter and files already available in the project, if present, to understand the intended structure and style. Do not hardcode reference content into user-generated output.

The preview must update when the user edits an event or changes its category.

Provide practical preview controls such as page navigation and zoom if supported by the existing implementation. Avoid building a complicated editing interface at this stage.

Allow the user to return to category review without losing their current work.

Before download, ensure the final document is generated from the latest reviewed data rather than stale preview state.

## 7. Step 5 — Download the output format selected by the user

Provide one straightforward export panel with a clear label such as **Download Your Newsletter**.

Offer appropriate output formats:

- **PDF** — the main, polished newsletter document.
- **DOCX** — an editable Word document, where supported.
- **Other formats** — only when the application can generate them reliably and they provide genuine value.

Do not display a format option that does not actually work.

If supporting multiple formats requires additional implementation, prioritize a high-quality PDF first, followed by editable DOCX.

The exported document must preserve event order, category headings, text, and associated images as accurately as the selected format permits.

For PDF export, ensure page breaks, image dimensions, fonts, and text wrapping are handled correctly. For DOCX export, preserve headings and images in a usable editable structure.

Use a sensible default filename, with an optional ability to rename the download.

Show clear feedback when export succeeds or fails. Do not claim a file has been generated until the browser has produced the download successfully.

## 8. Step 6 — Finish, clear, and start another file

After the user completes a download, show a simple completion screen.

The screen should clearly offer:

**Start New File**

The user should also be able to find an **Add New File** or **Start Over** action during the workflow, not just at the end.

Starting a new file must:

- Ask for confirmation if unsaved work would be discarded.
- Clear the current extracted events, categories, images, previews, temporary object URLs, and project-specific state.
- Reset progress and return to the upload screen.
- Never mix events from the previous file into the new file.
- Release browser resources and revoke temporary object URLs when they are no longer needed.

Support restarting if the user decides the current extraction is messy and wants to begin again from the original file.

If the user returns from the preview to edit categories, preserve their work. Only clear it when they explicitly start a new project or close/refresh the session according to the application's privacy model.

Make these controls easy to locate, but avoid filling the interface with duplicate reset buttons.

## 9. Mandatory privacy requirement — no server-side storage

This application must work as a **client-side-only document processing tool**.

Uploaded files, extracted event details, images, edits, and previews must not be uploaded to an application backend or stored in a database, cloud storage, analytics platform, or remote AI service.

Specifically:

- Do not introduce a backend or database for event content.
- Do not upload files to external processing APIs.
- Do not use remote AI services to classify documents. Use local extraction and transparent rule-based classification unless a suitable on-device solution is already available.
- Do not store uploaded content or extracted data in localStorage, sessionStorage, IndexedDB, or other persistent browser storage.
- Do not add telemetry, tracking, or content logging.
- Do not log extracted text, document contents, image data, or personal information in the console.
- Avoid transmitting sensitive document information through URLs or query parameters.
- Keep processing state in memory and generate output files in the browser.
- Clear in-memory state and temporary object URLs when starting a new project or leaving the workflow where appropriate.

Review the entire existing codebase and remove any existing functionality that violates these rules.

Dependencies may be loaded as required to run the application, but document contents must remain on the user's device.

Add a concise privacy note to the interface stating that uploaded files are processed locally in the browser and are not uploaded or saved by the application.

**Important:** Do not claim that the app stores absolutely nothing anywhere if browser memory, temporary downloads, browser history, hosting infrastructure, or third-party infrastructure are outside the application's control. Ensure the app itself does not transmit or persist user content, and describe the privacy guarantees accurately.

## 11. Technical quality and reliability

Review the actual existing implementation for bugs before adding new code.

Pay particular attention to:

- DOCX table extraction.
- PDF text extraction and OCR failures.
- Image-to-event associations.
- Incorrect, missing, or duplicate categories.
- Event edits not being reflected in the preview.
- Drag-and-drop corrupting or losing event data.
- Exporting outdated preview content.
- Missing images in the exported document.
- PDF page overflow, incorrect page breaks, and blank pages.
- Memory leaks from temporary object URLs.
- State leaking between projects.
- Unsupported file handling and malformed inputs.
- Responsive and keyboard-accessible category interactions.

Use a clear and consistent data model for events, category assignments, and associated images. Make sure changing category assignments does not create duplicate events or destroy event details.

Keep the existing React and TypeScript architecture unless there is a compelling technical reason to change it. Avoid unnecessary migrations, major dependency upgrades, and unrelated features.
