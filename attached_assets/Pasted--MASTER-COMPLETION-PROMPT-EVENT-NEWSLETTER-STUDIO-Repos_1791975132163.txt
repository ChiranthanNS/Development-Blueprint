## 2. Highest priority: correct duplicate-event detection

This requirement is critical.

I want to remove duplicate **events**, not duplicate participants.

The same participant can legitimately take part in many different events. Their participation in multiple events must never cause one event to be removed, merged, or flagged as a duplicate.

Review and improve `possiblySameEvent()` in `src/studio-utils.ts`, the duplicate queue in `src/App.tsx`, and the corresponding tests.

### Define event identity using relevant evidence

Compare event records using a combination of:

- Normalized event title.
- Event date or month, when available.
- Event description and distinctive subject matter.
- Event type.
- Venue or organizer, when available.
- Source information that can establish the records refer to the same event.

Normalize harmless formatting differences, including capitalization, repeated whitespace, punctuation, and common date-format variations where safe.

Do not treat these fields as proof of a duplicate:

- Participant names.
- Participants appearing in multiple events.
- Category alone.
- The same date alone.
- The same department, club, venue, or organizer alone.
- A generic description shared by unrelated events.

Participant lists can be preserved as event information, but they must not determine whether two event records refer to the same event.

Do not rely on an excessively broad description-similarity score. Many legitimate events use generic phrases such as “students participated enthusiastically” or “the event enhanced technical knowledge.”

### Apply conservative duplicate rules

1. Strong matches, such as the same normalized event title and compatible date/details, should be identified as likely duplicates.
2. Records with the same title but conflicting dates or clearly different event details must not be automatically discarded.
3. Different event titles should generally remain separate unless there is unusually strong evidence that they are merely formatting variants of the same title and refer to the same occurrence.
4. Missing dates should not automatically prevent matching, but the other evidence must be strong enough.
5. If evidence is uncertain, mark the records as possible duplicates and ask the user to decide.
6. Never silently discard a record because the classifier thinks it is similar to another.

Keep the existing lightweight approach unless a small, testable improvement is needed. Do not add an AI API or cloud processing service.

### Correct the duplicate-review interface

Provide a clear review dialog for each candidate showing:

- Existing event title, date, category, description, and source file.
- Newly imported candidate title, date, category, description, and source file.
- A clear explanation that the records appear similar.
- **Keep Existing, Discard New Duplicate** and **Keep Both Events** actions.

Where useful, allow the user to review or edit the new record before deciding.

Only remove the newly imported candidate after the user confirms that it is a duplicate. Preserve the existing event and all its original data.

When the user chooses Keep Both Events, add the new record without overwriting, merging, or replacing the existing event.

If the user discards a duplicate, keep accurate import diagnostics and review counts. Do not accidentally reduce unrelated warning counts or remove other records.

Never create a global “delete duplicates” operation that removes records without giving the user a meaningful opportunity to review uncertain matches.

### Test duplicate behavior thoroughly

Add automated tests for at least the following cases:

- Exact duplicate event.
- Same title and date with harmless whitespace/capitalization changes.
- Same title but clearly conflicting dates.
- Different event titles on the same date.
- Different events with generic or similar descriptions.
- Same participant mentioned in two separate events.
- Same participant list but distinct events.
- Same event imported from two different files.
- Missing dates with otherwise strong matching evidence.
- Ambiguous records that should go to manual review.
- Keep Both preserves both complete event records.
- Discard Duplicate removes only the new candidate.
- Event images and source metadata remain associated with the correct event.

Ensure the tests explicitly prove that participant overlap does not cause a duplicate classification.
